# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Twitch Clip Portal is a static, no-backend Twitch clip viewer built with React + TypeScript + Vite. There is no server component — the Twitch Helix API is called directly from the browser, authenticated via Twitch's OAuth Implicit Grant flow (the only flow that doesn't require a backend to hold a client secret).

## Development

- `npm install` — install dependencies
- `npm run dev` — start the Vite dev server
- `npm run build` — type-check (`tsc -b`) and produce a production build
- `npm run preview` — serve the production build locally
- `npm run lint` — run oxlint

There is no test suite.

## Deployment (GitHub Pages)

Target repo: `twitch-clip-viewer`, deployed as a GitHub Pages **project site** at `https://<username>.github.io/twitch-clip-viewer/` (not a `<username>.github.io` user/org site, which would serve from the root instead).

- `vite.config.ts` sets `base: '/twitch-clip-viewer/'` **only for `vite build`** (checked via the `command` param passed to the config function) — the dev server still runs at `/`, so it doesn't disturb the Twitch app's existing `http://localhost:5173/` redirect URI registration. If the repo is ever renamed, update this to match.
- `vite.config.ts` also sets `build.outDir: 'docs'` — GitHub Pages' "Deploy from a branch" mode only lets you pick `/ (root)` or `/docs` as the serving folder (not an arbitrary path like `dist`), so the build output goes straight into `docs/` and is committed as part of the repo. `docs/` is intentionally **not** in `.gitignore` for this reason (neither is `dist`, left over from before this change — nothing generates it anymore).
- No GitHub Actions workflow exists yet — deployment is still a manual step (`npm run build`, then commit + push `docs/`), and git itself hasn't been initialized in this project.
- Whichever branch/folder ends up configured in the repo's Pages settings, add the production URL — `https://<username>.github.io/twitch-clip-viewer/` (exact match, including the trailing slash) — as an **additional** OAuth Redirect URL on the same Twitch app (alongside the existing localhost one; Twitch apps accept multiple registered redirect URLs). GitHub Pages serves HTTPS by default, which Twitch requires for any non-localhost redirect URI.

## Architecture

`App.tsx` calls `useChannelSearch()` (`src/hooks/useChannelSearch.ts`) and `usePlaylists()` (`src/hooks/usePlaylists.ts`) once each and hands pieces of them to `Header`, `ChannelResults`, `Player`, and `PlaylistPanel` — a single instance of each hook called at the `App` level, rather than each component owning its own piece, is what keeps everything in sync (particularly: a clip added to a playlist from the search grid has to show up in the right column, and a clip clicked in a playlist has to be able to take over what `Player` shows).

When signed in, `main.stage` renders a **3-column `.workspace` grid** (`grid-template-columns: 600px minmax(500px, 1fr) 320px`, collapsing to one column under 1500px). The middle column's `1fr` max (not a fixed cap like `900px`, which was tried first and left dead space on wide screens once the column hit it) means it always claims exactly whatever width is left over after the fixed 600px/320px columns and gaps, on any viewport:
- **`.col-search`** (left, 600px — widened specifically so the clip grid's fixed `repeat(2, 1fr)` tiles have more room and more of the list is visible at once) — `ChannelResults`: the clip ID/URL/title search box and the clip list only (no longer the channel details card, see below).
- **`.col-player`** (middle, 500–900px rather than unconstrained `1fr`) — `ChannelDetails` (the channel avatar/name/badge/bio card) stacked above `Player`. It moved here from `.col-search` specifically to let that column grow wider without the card itself getting awkwardly wide too.
- **`.col-extra`** (right) — `PlaylistPanel`: user-created clip lists.

### Full-viewport-height layout with one internally-scrolling region
`#root` is `display:flex; flex-direction:column; min-height:100vh`, and `main.stage` is `flex:1; min-height:0` — together these make `main.stage` (and therefore `.workspace`, given `height:100%`) fill exactly the viewport height remaining below the header/local-time-note, rather than however tall its content happens to be. `.workspace` uses `align-items:stretch` (not `start`) so all 3 columns stretch to that same height. Only `.col-search`'s clip list is actually built to make use of the extra height: `.clip-list` is `flex:1; min-height:0` inside `.col-search`'s flex column, and `.clip-grid-scroll` inside *that* is also `flex:1; min-height:0; overflow-y:auto` — so the clip grid fills whatever vertical space remains after the search box/lookup field above it, scrolling internally, and the list visually reaches the bottom of the page regardless of viewport height. (This replaced an earlier flat `max-height:65vh` on `.clip-grid-scroll`, which didn't account for how much space the elements above it actually consumed and so left a gap at the bottom on most screens.) `.col-player` and `.col-extra` don't have their own internal scroll — if their content ever exceeds the stretched row height, they'll just overflow it naturally rather than clip, which is an acceptable fallback since neither is expected to grow unbounded the way a clip list can.

### "Now playing" is one concept shared by two independent clip sources
`Player`'s clip is `activeClip ?? searchCurrentClip` in `App.tsx`, where `searchCurrentClip` is `search.clips[search.playingIndex]` (as before) and `activeClip` is a plain `useState<Clip | null>` that a playlist clip click sets directly. Clicking a **search-grid** tile (`handleSearchPlay`) clears `activeClip` back to `null` first so it falls back to reflecting `search.playingIndex` again — the search grid's own tile-highlighting is untouched by any of this, still driven purely by `search.playingIndex`. This two-state arrangement (rather than, say, unifying everything into one array+index) exists because search results and playlist contents are genuinely different arrays that can both want to drive the same player at different times.

The original queue-based UI (`InputPanel`/`PasteTab`/`BrowseTab`/`ReelSidebar`/`ClipCard`, `useClipQueue`) still exists under `src/` but is unused — channel browsing was rebuilt as a one-shot search instead of an accumulating queue.

- **OAuth (Implicit Grant)** — `useTwitchAuth` (`src/hooks/useTwitchAuth.ts`) is the source of truth for auth state, backed by `sessionStorage` (`twitch_access_token`) so the session survives a refresh but clears when the tab/browser closes:
  - The Client ID is hardcoded in `src/config.ts` (`TWITCH_CLIENT_ID`) rather than entered by the user — Client IDs aren't secret (unlike a Client Secret, which this app never has, being Client Type: Public), so committing it is fine. `connect()` takes no arguments; it stashes a CSRF `state` nonce and redirects to `buildAuthorizeUrl()` (`src/lib/oauth.ts`) — `https://id.twitch.tv/oauth2/authorize` with `response_type=token`.
  - On mount, it checks `location.hash` via `parseAuthResponse()` for the `access_token`/`state` (or `error`) Twitch appends on redirect back, validates `state` against the stashed nonce, then strips the hash with `history.replaceState`.
  - Once a token is present it calls `fetchAuthenticatedUser()` (`src/lib/twitch.ts`) against `helix/users` (no query params → the token owner's own profile) both to confirm the token works and to get a display name + avatar; a failure here clears the stored token. `accessToken`, `clientId` (the constant, passed through for convenience), `displayName`, and `profileImageUrl` are all exposed for consumers.
  - `Header` (`src/components/Header.tsx`) shows the signed-in state as an avatar button (top right) that toggles a dropdown with the display name and a "Disconnect" button (click-outside closes it via a `mousedown` listener), and — also only when signed in — the channel search bar (`.header-search`: a "🔍" icon absolutely-positioned inside the input's left padding, clickable as the submit button) between the brand and the avatar. `TwitchAuth` (`src/components/TwitchAuth.tsx`) handles only the signed-out/connecting/error states: just a "Connect with Twitch" button, no fields.
  - The Twitch app backing `TWITCH_CLIENT_ID` needs **Client Type: Public** and an **OAuth Redirect URL** that exactly matches where the app is served (e.g. `http://localhost:5173/` in dev) — Twitch rejects mismatches by redirecting to the app's first registered redirect URI with an `error` param, which can look confusing (e.g. landing on an unrelated `http://localhost/`).
- **Channel search** — `useChannelSearch()` (`src/hooks/useChannelSearch.ts`) owns the search input plus `channelInfo`/`clips`/`playingIndex` state. Two separate presentational components consume it, rendered in two different `.workspace` columns by `App.tsx` (not nested under each other):
  - `ChannelDetails` (`src/components/ChannelDetails.tsx`, rendered directly in `.col-player`, stacked above `Player`) — avatar, display name (linked to `https://www.twitch.tv/<login>`), broadcaster type badge, bio, and member-since year, from `ChannelInfo` (`channelInfoFromHelix()` in `src/lib/twitch.ts`, mapped from `helix/users`). Follower count isn't shown: Helix's `channels/followers` endpoint requires the signed-in user to be a moderator (or the broadcaster) of the searched channel, so it 403s for arbitrary channels — not usable for a general channel-lookup feature like this one.
  - `ChannelResults` (`src/components/ChannelResults.tsx`, rendered in `.col-search`) — `ClipLookup` (once a channel is resolved), then `ClipList`, then `error` **last** (not first): an error (e.g. "No clips found matching...") renders *below* the clip list rather than above `ClipLookup`, specifically so showing/hiding it never shifts the search box's position — it used to render first and would push everything below it down each time it appeared.
  - `ClipList` (`src/components/ClipList.tsx`) — a "RECENT CLIPS (`clips.length`)"/"RESULTS (`clips.length`)" heading, switching on `isSearchResult` (state in `useChannelSearch`: `false` after the initial recent-clips fetch, flipped to `true` by `handleClipSearch()` — either the exact-match or the title-search branch — and back to `false` only by a fresh `handleSearch()` call) followed by the `ClipTile` grid; clicking a tile updates `playingIndex`. `.clip-grid` is a fixed `repeat(2, 1fr)` — the `.col-search` column width (600px) is sized specifically so 2 tiles fill it edge-to-edge with no leftover gutter (a fixed 2-up grid needs the column width tuned to it, unlike an auto-fill approach which adapts to whatever width is available). Each tile shows the clip's `creatorName` (Helix `creator_name` — the clip's creator, not necessarily the broadcaster) and a "↗" overlay icon (`.clip-tile-actions`) linking to `https://clips.twitch.tv/<slug>`, calling `stopPropagation()` so it doesn't also select the tile as active. The grid sits inside a `.clip-grid-scroll` wrapper (`flex:1; min-height:0; overflow-y:auto;` — see the full-viewport-height layout note above) so a long clip list scrolls internally instead of growing `main.stage`/the page — the negative `margin-right` cancels out the `padding-right` added for scrollbar breathing room, so the content doesn't visually shift relative to `ClipLookup` above it, which isn't in a scroll container.
  - **Category filter** — Helix clips only carry a `game_id` (mapped to `Clip.categoryId` in `clipFromHelix()`), not a category name, so `useChannelSearch` separately resolves names via `fetchGameNames()` (`src/lib/twitch.ts`, Helix's Get Games endpoint) in an effect keyed on `clips` — `knownCategoryIdsRef` (a `Set`, not state) tracks which ids have already been requested so repeated re-renders with the same `clips` don't refetch, and results land in `categoryNames: Record<id, name>` state. **The filter itself only ever operates on whatever's currently in `clips`** (the visible recent/search-result list, not the full background-indexed catalog) — a deliberate scope decision, since filtering the full index would need it to carry resolved category names too. `ClipList` builds the dropdown's options from unique names found in the current `clips` (plus an `"Uncategorized"` option for any with no `categoryId`), and filters by mapping `clips` to `{clip, i}` pairs *before* filtering so a filtered tile's `onPlay(i)` still refers to its original index in the unfiltered array — filtering the tiles must never change what index a click actually plays.
  - **There is deliberately no in-app clip download.** Helix has no documented way to get a clip's video file — only a thumbnail image, embed URL, and page URL. The old community trick of deriving an `.mp4` URL from the thumbnail URL's naming pattern (`...-preview-WxH.jpg` → `....mp4`) was tried and **confirmed dead against a real clip**: today's actual `thumbnail_url` looks like `https://static-cdn.jtvnw.net/twitch-video-assets/.../thumb-0000000000-1920x1080.jpg`, which doesn't match that pattern at all, so it silently produced no download link for any real clip. The only way to get an actual playable video URL today is Twitch's private internal GraphQL API (`gql.twitch.tv`, the same one `yt-dlp` uses) — confirmed working via live inspection, but it returns a signed, time-limited, session-tied URL (`...index.mp4?token=...&sig=...&expires=...`) that has to be fetched fresh per download rather than derived from anything in Helix. Using it was explicitly declined (it's Twitch's private web-client API, not their public Developer API). Don't re-attempt the thumbnail-derivation trick — it isn't a bug, it's structurally impossible with current Twitch data.
  - The date shown in both `ClipTile` and `Player`'s meta line is wrapped in `CopyDate` (`src/components/CopyDate.tsx`): clicking it copies a `YY.M.D` short date (`formatDateShort()` in `src/lib/format.ts`) to the clipboard and briefly shows "Copied!". Since the date is just one piece of a `·`-joined meta line that's otherwise plain strings, `joinParts()` (`src/lib/joinParts.ts`) interleaves the separator between mixed text/element children — plain `Array.join()` doesn't work once one part needs to be a clickable element instead of a string.
  - `handleSearch()` calls `fetchUserByLogin()` then `fetchRecentClipsForBroadcaster()` (both `src/lib/twitch.ts`) as two separate steps (rather than the combined `fetchChannelClips()`, which still exists as a thin wrapper over both, used by the unused `BrowseTab`) so the channel details can render as soon as the user is resolved, independent of the clips fetch. Since the hook is called unconditionally in `App` (so `Header` and `ChannelResults` share one instance) rather than only once signed in, the default-channel auto-search effect is keyed on `[accessToken]` and no-ops while it's still empty, firing once sign-in actually completes rather than on hook-mount.
  - `ClipLookup` (`src/components/ClipLookup.tsx`, shown once a channel is resolved) is a combined ID/URL/title search box, resolved by `handleClipSearch()` in `useChannelSearch` in priority order: (1) `extractSlug()` the input — if it looks like a clip URL or bare slug, try `fetchClipsByIds()` for an exact match; (2) if that didn't resolve to a real clip (wrong-looking slug, or a slug-shaped title that just happens to have no spaces), **fall through** to a title search instead of erroring immediately; (3) title search does a case-insensitive substring match against `title` across every clip in the background-built full-catalog index (see below) — Twitch has no server-side "search clips by title" endpoint, so this is entirely client-side. Every search **always replaces** `clips` wholesale (`setClips([found])` or `setClips(matches)`), even if the result is a clip that was already visible or an empty array — never prepend/append/re-select-in-place — so the results grid is always an exact reflection of the latest search. When a search yields zero matches, `ClipList` renders a "No results found." placeholder in place of the grid (gated on a `searching` prop so it doesn't flash between the old results clearing and the new ones — or the empty state — landing) instead of leaving stale tiles on screen. `handleClipSearch()` deliberately does **not** also set the `error` string for a zero-match result — that used to duplicate the same "no results" information as a second, separately-styled alert box below the placeholder, which read like a redundant popup; the placeholder alone (with an "…still indexing this channel's clips" variant when `indexingClips` is true, via a new `indexingClips` prop threaded through `ChannelResults` into `ClipList`) is the only feedback shown now. `error` is reserved for actual failures (e.g. a network/API error in the `catch` block).
  - **Full-catalog background index** — since title search needs more than the ~20 "recent" clips in the grid, `handleSearch()` also fires off `fetchAllClipsForBroadcaster()` (`src/lib/twitch.ts`) right after the recent-clips fetch, *not awaited* (fire-and-forget). It pages through the broadcaster's entire clip catalog via Helix's `after` cursor (capped at `maxPages = 50`, i.e. ~5000 clips, to bound worst-case request volume for very large channels; stops silently on any request failure, e.g. rate-limiting, rather than throwing, since it's best-effort), handing each page to a callback that merges into `allClipsMapRef` (a `Map<slug, Clip>` ref, not state — it doesn't need to trigger re-renders, only `handleClipSearch()` reads it at search time). `indexingClips` state drives a small "Indexing this channel's clips…" hint in `ClipLookup` while this is in flight, and a `searchGenRef` counter invalidates in-flight index-building from a *previous* channel search if the user searches a new channel before it finishes (checked before every state update in both the recent-clips path and the background page callback). `indexedCount` state mirrors `allClipsMapRef.current.size` (updated in the same page callback) purely so `ChannelDetails` can show a live "N clips loaded" stat — the ref alone wouldn't trigger a re-render, which is why this exists as state separately from it.
  - **Getting genuinely "recent" clips is non-obvious**: Helix's `clips` endpoint, called with no `started_at`/`ended_at`, returns the broadcaster's all-time most-viewed clips (sorted by view count) — not recent ones. `fetchRecentClipsForBroadcaster()` works around this by querying with a date range, widening it through `RECENCY_WINDOWS_DAYS` (30 → 90 → 365 → 730 days) until a window returns at least one clip, then sorts that window's results by `created_at` descending and takes the top `count`. A channel with no clips in ~2 years falls back to an undated (all-time top) query so the search doesn't come back empty. This means "recent" is only as recent as the channel's actual clip activity — a low-activity channel can still surface year-old clips, honestly.
- **`Player`** (`src/components/Player.tsx`) renders a Twitch embed iframe (`https://clips.twitch.tv/embed?clip=...&parent=...`) for the active clip. The `parent` param must match the hosting domain (`embedParent()` in `src/lib/twitch.ts` uses `location.hostname`) — Twitch embeds enforce this and fail silently if it's wrong.
- **Playlists** — `usePlaylists()` (`src/hooks/usePlaylists.ts`) is the source of truth: `playlists: Playlist[]` (`{ id, name, clips: Clip[] }`, `src/types.ts`) plus `activePlaylistId`, lazy-initialized from and written back to `sessionStorage` (`twitch_playlists`) on every change — **session-only by design**, same convention as the OAuth token in `useTwitchAuth`, deliberately not `localStorage`. Full `Clip` objects are stored directly (not just slugs), so a playlist's contents render independent of whether its source channel is still loaded/searched.
  - `ClipTile` (`src/components/ClipTile.tsx`) takes two *mutually exclusive* optional action props — `onAddToList` (renders a "+" icon, used by the search grid) and `onRemove` (renders a "×" icon, used by `PlaylistPanel`) — alongside the existing "↗" open-on-Twitch icon, all three sharing the same `.clip-tile-actions` overlay and `stopPropagation()` pattern so none of them also trigger `onPlay`.
  - Clicking "+" on a search-grid tile calls `handleAddToList()` in `App.tsx`, which adds to `playlists.activePlaylistId` if one exists, or else sets a `addToListError` string ("Create a list first...") shown as a `.status-msg.error` inside `PlaylistPanel` — there's no auto-creation of a default list, and no silent no-op.
  - `PlaylistPanel` (`src/components/PlaylistPanel.tsx`) owns the create/rename-list text inputs (both a controlled `useState` + submit-on-Enter/blur, no modal/prompt) and a `sortBy: 'date' | 'views'` **view-only** local state (not persisted — sorts a derived copy of `activePlaylist.clips` for display, descending in both cases; the stored array order itself is untouched). It reuses `.clip-grid` but overrides it to a single column (`.playlist-grid`) since `.col-extra` (320px) is narrower than `.col-search` (440px, tuned for the 2-up grid there).
  - Deleting the active playlist falls back to the first remaining one, or `null` if none are left — not explicitly requested, but included as the minimum complement to being able to create lists at all.
